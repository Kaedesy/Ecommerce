# 电商平台秒杀系统设计与改造方案

> 版本：V1.1（初版实现）\
> 依据：`Ecommerce-main.zip` 中现有商城源码\
> 目标：在保留现有限时购活动管理和普通订单链路的基础上，补齐 SKU
> 级秒杀下单、库存控制、异步创建订单、异常补偿与并发测试。\
> 状态说明：已完成代码改造、数据库迁移、本地手工端到端验证及 JUnit 并发集成测试；JMeter 压测尚未执行。

## 1. 现状盘点

### 1.1 已有能力

当前项目已经具备限时购/秒杀的活动管理与展示基础：

-   后台活动管理：`mall-swarm/mall-admin/.../SmsFlashPromotionServiceImpl.java`
-   后台场次管理：`SmsFlashPromotionSessionServiceImpl.java`
-   后台活动商品关联：`SmsFlashPromotionProductRelationServiceImpl.java`
-   首页秒杀活动查询：`mall-swarm/mall-portal/.../HomeServiceImpl.java`
-   首页秒杀商品
    SQL：`mall-swarm/mall-portal/src/main/resources/dao/HomeDao.xml`
-   移动端首页展示：`mall-app-web/src/pages/index/index.vue`

当前 `sms_flash_promotion_product_relation` 已有：

-   `flash_promotion_price`：限时购价格
-   `flash_promotion_count`：活动商品数量
-   `flash_promotion_limit`：每人限购数量

订单表 `oms_order.order_type` 已定义
`0=普通订单、1=秒杀订单`，但普通下单方法
`OmsPortalOrderServiceImpl.generateOrder()` 当前固定写入 `orderType=0`。

### 1.2 当前缺口

在 `mall-portal`
中，当前检索到的是首页秒杀信息查询，没有形成完整的秒杀交易接口和订单创建链路。现有活动商品关联以
`product_id` 为主，没有 SKU
级库存预占、用户购买限额、秒杀请求幂等和异步创建订单闭环。

普通订单已有可复用基础：

-   `OmsPortalOrderServiceImpl.generateOrder()`：普通订单创建事务
-   `lockStock()` + `PortalOrderDao.xml`：MySQL 条件 UPDATE 预占 SKU
    库存
-   `paySuccess()`：支付成功后确认库存
-   `cancelOrder()`：取消订单并释放普通订单库存
-   `oms_outbox_event` + `OutboxEventPublisher`：订单取消事件的 Outbox
    投递
-   `RabbitMqConfig`、`CancelOrderSender`、`CancelOrderReceiver`：TTL +
    死信队列实现普通订单延迟取消

**改造原则：保留普通订单流程，新增独立秒杀下单服务；不要把秒杀请求直接塞进普通购物车下单流程。**

## 2. 改造目标与范围

### 2.1 V1 目标

完成一条可测试、可解释的秒杀交易链路：

1.  管理端配置活动、场次、商品 SKU、秒杀价格、活动库存和用户限购数量。
2.  活动开始前，将活动库存从 SKU 可售库存中预留出来，并初始化 Redis
    秒杀库存。
3.  用户登录后提交秒杀请求，服务端校验活动、SKU、请求参数和用户身份。
4.  Redis Lua
    原子完成活动状态检查、库存预扣减、用户限购检查和请求令牌记录。
5.  通过 RabbitMQ 异步削峰，由消费者创建秒杀订单。
6.  MySQL 再次校验活动库存和用户限购，作为最终数据正确性的依据。
7.  支付、取消、超时关闭时正确流转秒杀库存。
8.  对重复请求、重复消息、消息失败和 Redis 补偿提供幂等处理。
9.  使用并发测试验证不超卖、不超限、不重复创建订单。

### 2.2 V1 暂不实现

为控制项目复杂度，第一版不做：

-   一个秒杀请求购买多个不同 SKU；V1 限定一次请求对应一个活动 SKU。
-   秒杀订单叠加普通优惠券、积分抵扣和购物车促销；V1
    使用活动配置的秒杀价。
-   多地域、多活 Redis 或跨机房容灾。
-   Kafka 替换 RabbitMQ。
-   复杂的预约、抽签、动态风控系统。

## 3. 总体架构

``` text
移动端商城
   |
   | POST /flash/order
   v
mall-portal
   |
   +--> Sa-Token 获取当前会员身份
   |
   +--> 创建/读取秒杀请求记录（幂等）
   |
   +--> Redis Lua
   |      - 活动是否可参与
   |      - 活动库存是否充足
   |      - 用户是否超过限购
   |      - requestNo 是否已处理
   |
   +--> 秒杀请求记录进入待发布状态
              |
              v
       FlashOrderPublisher
              |
              | Publisher Confirm
              v
       RabbitMQ 秒杀下单队列
              |
              v
       FlashOrderConsumer
              |
              +--> MySQL 最终库存校验
              +--> MySQL 用户限购校验
              +--> 创建 oms_order（order_type=1）
              +--> 创建 oms_order_item
              +--> 关联秒杀请求
              +--> 写入现有订单取消 Outbox 事件
              |
              v
          秒杀订单创建成功
              |
       +------+------+
       |             |
       v             v
    支付成功        取消/超时
       |             |
       v             v
  reserved->sold   释放活动预占
  扣减实际库存     活动未结束则归还 Redis
                  活动已结束则释放物理锁定库存
```

### 核心职责边界

  ----------------------------------------------------------------------------------------------
  组件                                职责
  ----------------------------------- ----------------------------------------------------------
  MySQL                               活动配置、最终库存、订单、用户限购和请求状态的权威数据

  Redis + Lua                         秒杀入口的快速库存预扣减、用户限购预判、请求令牌幂等

  RabbitMQ                            秒杀请求异步排队和削峰

  秒杀请求表                          持久化请求、幂等键、发布状态和订单关联，承担可靠投递依据

  现有订单 Outbox                     继续负责秒杀订单创建后的超时取消事件

  补偿任务                            处理 Redis 预扣减后订单创建失败、订单取消后的库存归还
  ----------------------------------------------------------------------------------------------

Redis 预扣减是流量入口控制，不是最终库存凭证。**MySQL
条件更新仍然是最终防止超卖的兜底。**

## 4. 数据模型改造

### 4.1 秒杀商品关联增加 SKU 维度

当前活动商品关联表只关联 `product_id`，但真实库存位于
`pms_sku_stock`。建议在 `sms_flash_promotion_product_relation` 增加：

  ------------------------------------------------------------------------------------
  字段                    类型建议                说明
  ----------------------- ----------------------- ------------------------------------
  `product_sku_id`        BIGINT                  本次活动对应的具体 SKU

  `reserved_count`        INT                     已创建订单、尚未支付的秒杀预占数量

  `sold_count`            INT                     已支付成交数量

  `stock_status`          VARCHAR(16)             DRAFT / PREPARING / READY / ACTIVE /
                                                  ENDED
  ------------------------------------------------------------------------------------

继续使用已有字段：

-   `flash_promotion_count`：活动总配额
-   `flash_promotion_limit`：每个会员限购数量
-   `flash_promotion_price`：秒杀成交单价

V1 约定：一条活动商品关联记录对应一个 SKU；同一 SPU 的不同 SKU
可以配置成多条活动关联记录。管理端需要增加 SKU
选择，并在活动进入准备/上线状态后禁止随意修改 SKU 和库存配额。

建议增加唯一约束，避免同一活动、场次、SKU 重复配置：

``` sql
UNIQUE KEY uk_promotion_session_sku
(flash_promotion_id, flash_promotion_session_id, product_sku_id)
```

> 历史活动记录的 `product_sku_id`
> 需要允许为空以兼容旧数据；新建并参与秒杀的记录必须填写 SKU。

### 4.2 秒杀请求表 `sms_flash_promotion_request`

该表负责请求幂等、持久化排队和订单关联，避免 Redis
预扣减成功后应用宕机导致请求丢失。

建议字段：

  -----------------------------------------------------------------------
  字段                                说明
  ----------------------------------- -----------------------------------
  `id`                                主键

  `request_no`                        全局唯一请求号，作为消息幂等标识

  `member_id`                         会员 ID

  `promotion_relation_id`             活动 SKU 关联 ID

  `product_sku_id`                    SKU ID

  `quantity`                          秒杀数量，V1 默认限制为
                                      1，也可按配置限购

  `idempotency_key`                   客户端幂等键

  `request_hash`                      规范化请求参数的 SHA-256 摘要

  `status`                            INIT / READY / PUBLISHED /
                                      PROCESSING / ORDER_CREATED /
                                      REJECTED / RESTORE_PENDING /
                                      RESTORED

  `order_id`                          创建成功后的订单 ID

  `fail_reason`                       失败原因

  `create_time`、`update_time`        创建和更新时间
  -----------------------------------------------------------------------

建议约束：

``` sql
UNIQUE KEY uk_request_no (request_no),
UNIQUE KEY uk_member_idempotency (member_id, idempotency_key),
UNIQUE KEY uk_order_id (order_id)
```

`request_no` 用于消息消费幂等；`member_id + idempotency_key`
用于防止同一会员重复提交同一业务请求。

### 4.3 用户限购表 `sms_flash_promotion_user_limit`

Redis 负责入口限购预判，MySQL 负责最终限购校验。

建议字段：

  字段                      说明
  ------------------------- ----------------------
  `id`                      主键
  `promotion_relation_id`   活动 SKU 关联 ID
  `member_id`               会员 ID
  `reserved_count`          已创建但未支付的数量
  `bought_count`            已支付购买数量
  `update_time`             更新时间

唯一约束：

``` sql
UNIQUE KEY uk_promotion_member (promotion_relation_id, member_id)
```

消费者通过条件更新控制：

``` sql
UPDATE sms_flash_promotion_user_limit
SET reserved_count = reserved_count + #{quantity}
WHERE promotion_relation_id = #{relationId}
  AND member_id = #{memberId}
  AND reserved_count + bought_count + #{quantity} <= #{limit};
```

实际实现时先 `INSERT IGNORE` 初始化用户记录，再执行条件
UPDATE，并检查影响行数。

### 4.4 订单关联

继续使用已有字段：

``` text
oms_order.order_type = 1
```

订单商品继续写入 `oms_order_item`，保存 SKU、商品快照、数量和秒杀价格。

通过 `sms_flash_promotion_request.order_id`
关联秒杀请求与订单，避免只依靠订单类型无法追溯活动 SKU、用户限购记录和
Redis 预占令牌。

## 5. 秒杀库存设计

### 5.1 物理库存预留

当前普通订单库存逻辑使用：

``` text
可售库存 = pms_sku_stock.stock - pms_sku_stock.lock_stock
```

普通订单通过 `lockStock()` 增加 `lock_stock`，支付时通过
`confirmSkuStock()` 同时减少 `stock` 和 `lock_stock`，取消时释放
`lock_stock`。

为了防止普通订单把秒杀库存买走，活动准备阶段需要先从 SKU
可售库存中预留活动配额：

``` sql
UPDATE pms_sku_stock
SET lock_stock = lock_stock + #{flashCount}
WHERE id = #{skuId}
  AND stock - lock_stock >= #{flashCount};
```

影响行数为 1 才能预留成功。活动 SKU
配额应在同一个数据库事务中登记，失败则整体回滚。

这意味着：

-   普通订单只能购买扣除活动配额后的可售库存。
-   秒杀订单使用已经预留的活动库存，不再调用普通订单的
    `lockStock()`，避免重复锁定。
-   秒杀支付成功时，复用现有 SKU
    实际库存确认逻辑：`stock - quantity`、`lock_stock - quantity`。
-   秒杀取消时必须根据活动状态决定是否释放物理锁定库存，不能无条件调用普通订单的
    `releaseOrderInventoryLock()`。

### 5.2 活动库存状态

对每条 SKU 活动关联记录维护：

``` text
活动总配额 = flash_promotion_count
已预占量   = reserved_count
已售数量   = sold_count
可再次抢购 = 总配额 - 已预占量 - 已售数量
```

创建秒杀订单时增加 `reserved_count`；支付成功时
`reserved_count--`、`sold_count++`；取消订单时 `reserved_count--`。

### 5.3 活动开始和结束

**活动开始前：**

1.  校验活动、场次、SKU、活动数量和限购数量。
2.  通过 MySQL 条件 UPDATE 预留物理库存。
3.  初始化 Redis 库存和用户计数。
4.  Redis 初始化成功后将活动状态推进到 READY。
5.  到达开始时间后将活动切换为 ACTIVE。

初始化必须幂等，不能在应用重启或定时任务重复执行时把 Redis
已扣减库存重置为初始值。

**活动结束时：**

1.  将活动状态切换为 ENDED，阻止新请求。
2.  禁止 Redis 再接受预扣减。
3.  释放未预占、未售出的剩余活动配额。
4.  已创建的待支付订单继续按订单超时策略处理。
5.  活动结束后才取消的订单，释放其对应的物理锁定库存，不再把库存放回已关闭活动的
    Redis 库存池。

活动结束与支付/取消并发时，必须通过数据库状态条件更新和事务保证只释放一次。

## 6. Redis Key 与 Lua 脚本

### 6.1 Key 设计

V1 一条活动关联记录对应一个 SKU，可以使用活动关联 ID 作为库存隔离维度。

建议 Redis Cluster 兼容的 Hash Tag：

``` text
flash:{relationId}:stock
flash:{relationId}:users
flash:{relationId}:status
flash:{relationId}:request:{requestNo}
```

同一活动 SKU 的 Key 使用相同 `{relationId}`，确保 Lua 涉及的 Key 在
Redis Cluster 中位于同一个 slot。

### 6.2 预扣减 Lua 的原子步骤

脚本输入：活动关联 ID、会员 ID、请求号、购买数量、限购数量。

执行顺序：

1.  检查 requestNo 是否已有处理结果；若已有则返回原结果，不重复扣减。
2.  检查活动状态是否为 ACTIVE。
3.  检查活动库存是否大于等于购买数量。
4.  检查当前会员已预占/购买数量加本次数量是否超过限购。
5.  扣减活动库存。
6.  增加会员计数。
7.  写入 requestNo 对应的预占状态、会员和数量，并设置合理过期时间。
8.  返回成功及剩余库存。

上述操作必须在同一段 Lua 脚本中执行，不能拆成多条客户端命令。

### 6.3 库存补偿 Lua

补偿脚本必须以 `requestNo` 为幂等依据：

1.  读取请求预占状态。
2.  只有状态为 RESERVED 的请求允许补偿。
3.  如果活动仍为 ACTIVE，归还 Redis 库存。
4.  减少对应会员的 Redis 预占计数。
5.  将请求令牌标记为 RESTORED。
6.  重复执行时直接返回已补偿，不再次增加库存。

如果活动已经
ENDED，不再把库存加回活动池；物理库存释放由数据库活动关闭流程负责。

### 6.4 Redis 与 MySQL 的职责

-   Redis：高并发入口快速拦截、预扣减和限购预判。
-   MySQL：最终活动库存、用户限购、订单及支付状态的权威记录。

不能只依赖 Redis 计数判断最终是否成功创建订单。

## 7. 秒杀请求与 RabbitMQ

### 7.1 为什么不直接在接口中创建订单

秒杀流量可能瞬间集中到订单服务。如果每个请求都同步执行复杂的订单事务，会放大数据库瞬时压力。

因此入口完成 Redis 预扣减后，将请求放入
RabbitMQ，由消费者控制订单创建速度，实现异步削峰。

### 7.2 新增独立队列

不要复用现有普通订单取消队列 `mall.order.cancel`。

建议新增：

  组件                   建议名称
  ---------------------- ---------------------------
  Exchange               `mall.flash.exchange`
  Routing Key            `mall.flash.order.create`
  Queue                  `mall.flash.order.create`
  Dead Letter Exchange   `mall.flash.dlx`
  Dead Letter Queue      `mall.flash.order.dlq`

秒杀创建消息只传 `requestNo`，消费者再从 MySQL
查询请求详情，避免客户端或消息体携带价格、会员身份等不可信业务数据。

### 7.3 发布可靠性

秒杀请求先持久化为 INIT。Redis Lua 预扣减成功后，将请求状态推进为
READY。

`FlashOrderPublisher` 定时扫描 READY 请求：

1.  认领请求，使用状态条件更新或租约避免多实例重复领取。
2.  发送 RabbitMQ 持久化消息，消息携带 requestNo。
3.  等待 Publisher Confirm，并检查 Mandatory Return。
4.  确认成功后将请求标记为 PUBLISHED。
5.  发送失败时保留可重试状态，使用退避策略重试。

如果消息已经被 Broker 接收，但应用在更新 PUBLISHED
前宕机，可能重复发布。因此消费者必须幂等。

### 7.4 消费者处理

`FlashOrderConsumer` 的业务事务：

1.  根据 requestNo 查询并锁定请求记录。
2.  如果请求已经 ORDER_CREATED，直接返回，避免重复创建订单。
3.  校验活动仍允许创建订单、SKU 和会员信息有效。
4.  使用 MySQL 条件 UPDATE 检查并增加活动 reserved_count。
5.  使用用户限购表条件 UPDATE，确认未超过购买上限。
6.  创建 `oms_order`，设置 `order_type=1`。
7.  创建
    `oms_order_item`，商品价格使用数据库中的秒杀价格，不信任前端传价。
8.  将 request 关联 order_id，并标记 ORDER_CREATED。
9.  通过现有 `sendDelayMessageCancelOrder(orderId)`
    在同一订单事务中写入订单取消 Outbox 事件。
10. 事务提交后 ACK 消息。

如果遇到数据库连接中断等临时异常，应让消息进入重试流程，不要立即补回
Redis
库存。只有明确的业务拒绝或超过最大重试次数的终态失败，才进入补偿流程。

## 8. 订单支付、取消与库存补偿

### 8.1 秒杀订单支付成功

现有 `paySuccess()` 已经完成订单状态迁移，并调用
`confirmOrderInventory()` 扣减真实 SKU 库存。

秒杀订单需要额外完成：

-   活动 `reserved_count` 减少。
-   活动 `sold_count` 增加。
-   用户限购记录从 reserved_count 转为 bought_count。
-   秒杀请求记录更新为已完成/已支付关联状态。

这些数据库操作与订单支付状态迁移放在同一个本地事务中。

### 8.2 秒杀订单取消

现有 `cancelOrder()` 会调用
`releaseOrderInventoryLock()`。秒杀订单不能直接沿用这段逻辑，因为活动配额在活动期间仍然需要保持物理锁定。

取消时按活动状态分支：

**活动仍在进行：**

-   订单状态从待支付迁移到已关闭。
-   活动 reserved_count 减少。
-   用户 reserved_count 减少。
-   通过可靠补偿任务归还 Redis 库存和用户计数。
-   不减少 SKU 的活动总物理锁定配额。

**活动已经结束：**

-   订单状态迁移成功后，减少活动 reserved_count。
-   减少 SKU 的 `lock_stock`，释放该笔未成交的物理库存。
-   不恢复已关闭活动的 Redis 库存。

支付和取消仍然使用现有条件状态迁移：

``` sql
UPDATE oms_order
SET status = #{targetStatus}
WHERE id = #{orderId}
  AND status = 0;
```

只有成功迁移的一方可以执行对应库存副作用。

### 8.3 Redis 补偿可靠性

Redis 与 MySQL 不属于同一个本地事务，不能在数据库事务中简单地直接 `INCR`
后就认为补偿完成。

建议在数据库事务中把请求状态改为
RESTORE_PENDING，再由独立补偿任务执行幂等 Lua。补偿成功后标记 RESTORED。

补偿任务应覆盖：

-   Redis 预扣减成功，但应用在更新请求状态前宕机：请求保留 INIT，恢复任务以同一 requestNo 重放 Lua（令牌需保留足够长），根据原结果推进 READY，不能直接补库存。若 Redis 数据丢失，则暂停活动并按 MySQL 请求/订单数据重建库存，不能自动按初始值覆盖。
-   消费者业务拒绝，订单未创建。
-   消费者达到最大重试次数，消息进入 DLQ。
-   订单取消，活动仍在进行。
-   活动结束与补偿任务同时发生。

### POST `/flash/order` 示例

请求头：

``` http
Idempotency-Key: 业务请求唯一键
```

请求体：

``` json
{
  "promotionRelationId": 1001,
  "quantity": 1,
  "receiveAddressId": 10
}
```

会员 ID 从 Sa-Token 当前登录态获取，不能信任前端传入。收货地址 ID 必须由会员提供，并在服务端校验归属；请求表需要持久化地址快照或地址 ID，建单时再次校验地址仍有效。秒杀订单 V1 不使用优惠券和积分，避免与普通结算优惠并发争用。

返回结果建议区分：

-   `ACCEPTED`：Redis 预扣减成功，等待异步创建订单。
-   `ORDER_CREATED`：订单已创建。
-   `SOLD_OUT`：库存不足。
-   `LIMIT_EXCEEDED`：超过限购。
-   `ACTIVITY_NOT_ACTIVE`：活动未开始或已结束。
-   `REJECTED`：业务校验失败。

前端收到 ACCEPTED 后，通过 requestNo 轮询查询结果；不要把"Redis
预扣减成功"直接显示为"抢购成功"。

## 13. 关键风险与设计约束

1.  **Redis 与 MySQL 不存在跨库原子事务。** 需要请求持久化、幂等
    Lua、补偿任务和定期对账，不要声称 Redis 预扣减和 MySQL
    订单事务天然强一致。
2.  **不能只依赖 Redis 防超卖。** MySQL
    活动库存条件更新必须保留，作为最终业务约束。
3.  **不能复用普通订单库存释放逻辑。** 普通订单取消直接释放
    `lock_stock`；活动期间取消秒杀订单应先归还活动池，活动结束后才释放物理活动配额。
4.  **不能把秒杀价交给前端决定。**
    消费者必须从数据库读取活动价格，并将其写入订单明细快照。
5.  **不能把 Publisher Confirm 当成消费者处理成功。** Confirm 只确认
    Broker 接收；消费者仍然需要幂等和重试。
6.  **不能把 Redis 库存初始化放在每次应用启动时无条件执行。**
    必须通过活动状态、版本号或初始化标记防止覆盖正在运行的库存。
7.  **活动 SKU 必须和真实库存 SKU 对应。** 当前活动关联表只有
    product_id，必须补 SKU 维度，否则无法准确预留和扣减具体规格库存。
8.  **支付与取消竞争必须沿用条件状态迁移。**
    任何库存副作用都只能由成功迁移状态的一方执行。
